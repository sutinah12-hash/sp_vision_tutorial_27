- `60e11bb`：将里程计和控制输入放入单独的互斥回调组。

## 1. Why vectorization is equivalent

原始 `_sample_obstacle_mask` 对每个格子执行：

1. 用局部网格原点、格子索引和分辨率得到格子中心世界坐标。
2. 转成原始地图像素坐标，将 y 轴翻转到图像坐标系。
3. 使用半整数取偶舍入，再判断边界并查询障碍值。

现在分别批量计算行/列坐标，使用 `np.rint` 保持同样的半整数取偶规则，再用数组索引读取原地图。边界外仍为原版的 False。运算顺序没有合并成可能改变边界舍入的替代公式。

没有降低分辨率，没有跳过格子，没有减小局部地图，也没有添加可能过期的地图缓存。动态机器人障碍盖章、距离变换和代价转换保持原函数。

`scripts/verify_sampling_equivalence.py` 从官方基线 Git 提交读取真正的旧函数，而不是另写一个简化参考。测试包含随机原点、边界、半格位置及其相邻浮点数、空网格、不同地图原点与分辨率，逐格比较障碍布尔值和动态障碍盖章后的代价值；随后校验受保护文件的 SHA-256。

首轮 190 个案例、506861 个格子均一致。当前机器上，完整 80×80 采样的中位时间从约 61 ms 降至约 0.12 ms。该倍数只代表这个采样函数，不代表整个导航程序提速相同倍数。

## 2. Why callback grouping helps

官方两个定时器共用默认互斥回调组。地图计算占用该组时，里程计和速度命令回调只能等待。

优化后地图回调仍在默认组；里程计、速度命令、云台命令和底盘模式命令在另一个互斥组。两组可以交替或并行获得执行机会，但同组内仍不重入。原来的 `SimRobot.lock` 继续保护位置快照、运动步进和控制输入。

没有改 `publish_hz`、`pub_hz` 或 `odom_hz`，它们仍为 30.0。调度改善不保证 Python 在所有电脑上都能达到恰好 30Hz，因此每次正式试验还记录实际接收的里程计频率。

## 3. Reproduce the verification

在已经编译并 source 工作空间的终端执行：

```bash
python3 scripts/verify_sampling_equivalence.py --out results/sampling_check_01
```

输出目录必须是新的，以免覆盖旧证据。`verification.json` 包含逐格比较数量、计时和未修改文件的哈希。原版实现一直保存在 Git 历史中，两个优化提交可以分别审查和回退。

调度可能改变实际消息时序，因此不能仅凭逐格等价就声称整段轨迹完全不变。MPC 和 PID 必须在相同优化后的仿真器、相同配置下重新测试；不能把优化前后的成绩混在一起作公平对照。
