## 1. 图像生命周期与所有权

解释本项目中图像源为什么会复用缓冲区，以及 `cv::Mat` 的普通复制对底层像素数据
意味着什么。说明你的修改让一个 `Frame` 在进入队列后拥有什么，并解释为何后续读取
不会再改变它。

图像源用 `buffer_` 模拟相机 SDK 管理的复用缓冲区。每次读取时，新图像都会写入这块
缓冲区，因此它的内容会随着下一次采集改变。`cv::Mat` 的普通赋值只复制一个小型矩阵
头并增加底层数据的引用计数，不会复制像素；如果把 `buffer_` 直接赋给 `Frame`，旧帧
和图像源仍会观察同一块像素数据。

我在生成帧时使用 `buffer_.clone()`。它为该帧分配独立像素存储并复制当前内容，
所以进入队列的 `Frame` 拥有独立的图像数据。之后 `buffer_` 被下一次采集覆盖，
也不会影响已经入队的帧及其校验值。

## 2. 并发处理与恰好一次

结合 `BlockingQueue` 的 `push`、`pop` 和 `close` 行为，解释多个 worker 如何分工。
为什么你的实现既不会漏掉已经入队的帧，也不会重复处理同一帧？输入耗尽时，正在等待
以及仍在处理数据的 worker 分别会怎样？

producer 把每个 `Frame` 移动到 `BlockingQueue` 中。`push()` 持锁插入元素后只
唤醒一个等待者；`pop()` 在锁内移动队首并立即删除它。即使多个 worker 同时等待，
一个队列元素也只能被一次成功的 `pop()` 取走，因此不会重复处理。producer 只为
每次成功读取执行一次 `push()`，所以不会主动漏掉输入帧。

输入耗尽后 producer 调用 `close()`，所有等待者都会被唤醒。队列中仍有元素时，
`pop()` 会继续返回这些元素，让 worker 把已入队数据全部处理完；只有队列为空时
才返回 `false`，对应 worker 随即退出。正在处理的 worker 会保存当前结果，然后
再次调用 `pop()`，继续取剩余帧或正常退出。

## 3. 共享统计数据

指出哪些线程会读写 `Statistics`。解释原实现中的竞争为什么可能导致错误结果，并说明
你的同步方案提供了什么保证。还应说明取得快照时为什么是安全的。

producer 更新 `produced`；多个 worker 并发更新 `processed`、`saved` 和
`corrupted`；主线程通过 `snapshot()` 读取全部计数。原递增操作包含读、改、写，
多个线程交错时可能读取同一个旧值，随后覆盖彼此的结果，导致计数丢失；无同步读取
本身也会构成数据竞争。

我给 `Statistics` 增加了一把互斥锁。每次递增都在持锁期间完成，所以同一时刻只有
一个线程能修改计数。`snapshot()` 也持有同一把锁，在一个临界区内复制四个字段，
因此取得的是无数据竞争且内部一致的快照。

## 4. 线程关闭协议

分别描述以下两条路径中的事件顺序，并解释为什么不会发生 `std::terminate`、悬空访问
或永久等待：

1. 调用者执行 `start()` 后显式调用 `wait()`；
2. 调用者执行 `start()` 后不调用 `wait()`，直接让 `Pipeline` 析构。

如果你的实现允许某个生命周期方法被重复调用，也请说明其行为；如果不允许，请说明前置条件。

显式调用 `wait()` 时，主线程先等待 producer。producer 读完输入、将最后一帧入队
并关闭队列后结束；随后主线程逐一等待 worker。worker 会排空关闭前已入队的帧，
然后因 `pop()` 返回 `false` 而退出，所以所有线程最终都能被 `join()` 回收。

如果调用者不执行 `wait()`，`Pipeline` 的析构函数会主动调用它，执行相同的关闭
顺序。对象成员只有在线程全部结束后才开始销毁，因此不会销毁仍为 joinable 的
`std::thread`，也不会让线程访问已经析构的 `queue_`、`source_` 或统计对象。

`wait()` 可以重复调用，也可以在 `start()` 前调用；它只对仍然 `joinable` 的线程
执行 `join()`，其余情况等价于无操作。`start()` 的前置条件是只调用一次，第二次
调用会抛出 `std::logic_error`。如果启动线程的过程中发生异常，代码会先关闭队列、
回收已经创建的线程，再把异常继续抛给调用者。这样既不会触发 `std::terminate`，
也不会留下悬空访问或永久等待。
