# Understanding our MPC

## 1. Exact type

本项目使用**带固定输入延迟补偿的线性约束模型预测控制**，简称带延迟补偿的 LMPC。它是本项目自己实现的速度跟踪器，不是直接加载 Nav2 MPC、不是神经网络，也不是完整非线性 MPC。

严格区分：预测模型是线性的；目标函数是凸二次函数；每一步输入受到二维速度圆盘约束，所以整体是凸二次约束优化问题（QCQP），不应把它说成只有线性约束的标准 QP。实现采用投影加速梯度迭代，最多 100 次，求得近似解；没有使用商业求解器，也不宣称每次精确达到全局最优。

核心位置：`src/sp_controller_server/plugins/tracking_math.hpp` 的 `VelocityMpc`，ROS 封装在同目录的 `tracking_controller.cpp`，实际运行参数来自 `src/sp_nav_bringup/config/nav_params.yaml`。头文件内的默认值不等于 launch 后读入 YAML 的值。

## 2. What it predicts

机器人状态是世界坐标下的位置和速度：

```text
state = [px, py, vx, vy]
input = [ux, uy]  # 期望世界坐标速度，不是电机电压或力矩
```

对 x、y 两个方向都使用：

```text
alpha = exp(-dt / tau)
v[k+1] = alpha * v[k] + (1-alpha) * u[k]
p[k+1] = p[k] + dt * v[k+1]
```

`v` 是真实速度，`u` 是期望速度。指令变为 1 m/s，不意味着下一瞬间车就到了 1 m/s。`tau` 表示这种速度响应的迟缓程度。

这里 `dt=0.07 s`、`tau=0.315 s`，所以 `alpha` 约为 0.801。忽略延迟、从静止给 1 m/s 时，一步后模型预测的速度约为 0.199 m/s，而不是 1 m/s。这正是不能简单把“速度指令”当“实际速度”的原因。

`tau` 和延迟不是随意填写的：使用课程原版动力学库做固定朝向的离线阶跃试验，拟合得到延迟约 0.2147 s、时间常数约 0.3145 s。导航时仍使用未改动的原版动力学，只是在控制器内部用较简单的模型预测它。

## 3. Why keep a delay queue?

假设现在才发现前面需要减速，刚发出的减速命令不会立刻抵达执行器。之前发出的几条加速命令仍会执行。

因此保存已发送的历史命令，预测开头的 3 步固定为延迟队列：`3 × 0.07 = 0.21 s`。优化器不能把这 3 步假装改成刹车，只能从第一个还没发出的命令开始选择。返回的是第 4 个预测时段的命令，而不是队列里已经发出的旧命令。

实现使用发送时间检索历史命令，而非简单假定 ROS 每次回调间隔都绝对相等；但延迟模型仍然是近似固定值，并不是对全部系统延迟的在线辨识。

## 4. What does the cost function prefer?

在 28 个预测步上累加四种代价：

```text
24  * position_error^2
1.5 * velocity_error^2
0.7 * command_change^2
0.02 * command_magnitude^2
```

最后一步的位置权重增大为 72。二维向量的平方表示 x/y 两个分量平方之和。

- 位置误差：尽量沿规划路径走，不在走廊里偏离太多。
- 速度误差：跟上路径生成的参考速度，不只停在附近。
- 指令变化：避免相邻指令反复大幅加减速。
- 指令幅度：在效果近似时不发无必要的大指令。

权重是在当前单位和场景下的设计选择，不是通用最佳值。速度参考会根据路径曲率和终点剩余距离减速，MPC 不是始终满速冲到终点。

## 5. Prediction interval is not the control interval

预测 28 步，每步 0.07 s，总计约 1.96 s，其中开始 0.21 s 是已发送指令的延迟段。

控制器配置以 50 Hz 调用，即目标每 0.02 s 重新优化一次；实际回调频率受虚拟机调度影响。每次只发一个当前控制量，不会一次性把未来两秒的全部动作发给机器人。下次用新测到的位置和速度重新预测，因此称为“滚动时域”。

长时域和密集预测可以增加计算量，并不必然改善实际跟踪。当前选择兼顾这个仿真器约半秒量级的延迟/响应过程、走廊弯道和 VM 的计算预算。

## 6. Constraints and coordinate frames

每步预测输入满足 `sqrt(ux^2 + uy^2) <= 1.25 m/s`。不能仅分别把 x/y 限为 1.25，否则斜向合速度会超过上限。

最终输出还施加 `1.7 m/s^2` 的指令变化限幅。**这项最终限幅并没有完整加入凸 MPC 的预测优化约束中**，因此会有模型与实际输出不完全一致的情况；不能声称实现了全部动力学约束的严格最优控制。实验采样控制器在候选轨迹中额外考虑这一限幅，这是二者的重要区别之一。

MPC 在 `map` 世界坐标里决定该往哪个方向移动，但机器人接收的是旋转中的 `base_link` 坐标指令。因此最后按当前 yaw 做逆旋转。否则机器人转身后，相同的“向前”指令会指向不同世界方向。

## 7. Why choose this for this homework?

这个作业的重点是固定地图中全向底盘的平滑跟踪。A* 已负责寻找可行路线；控制器主要面对延迟、转弯误差和终点停车。

线性模型结构简单，能凝聚成小规模优化；当前 28 步、二维输入约为 56 个标量，比引入训练数据或复杂非线性模型更容易检查、解释和在 VM 中调试。它利用预览，能够提前改变方向，而不只是等当前位置偏离后再纠正。

这些是采用 LMPC 的工程理由，不意味着它普遍优于 PID 或所有更先进算法。重复试验及失败率才是当前实现的评价依据，单轮结果不能作为普遍性能结论。

## 8. Boundaries and next experiments

- 预测模型是对原版动力学的简化，辨识只使用固定朝向阶跃，不完整描述旋转底盘、碰撞等非线性耦合。
- 控制优化器没有直接加入全部障碍约束；避障主要依靠 A*、膨胀地图和安全平滑，不构成严格的整机无碰撞保证。
- 实际受调度、测量时序和模型误差影响，不能保证所有电脑都得到相同耗时。
- 已增加 `SamplingController` 做平滑采样预测对照。它是受 MPPI 启发的实验实现，不是完整 SVG-MPPI。
- NMPC/iLQR、带障碍代价的 MPPI、学习辅助模型等可作为进一步研究方向；尚未实现的部分不能写成已完成或已胜出。

一句话复述：**A* 决定走哪条路；带延迟补偿的 LMPC 用一个简化运动模型，反复预测接下来约两秒怎么走，以兼顾贴合路径、速度和平滑指令。**
